Аудит по плану «Фаза 1. Безопасность и аудит» (документ «Итоги проверки и список доработок», 18.08.2026).
База: коммит `025a79e`. Дата обхода: 03.10.2026. **Статус: ожидает согласования ревьюером.**

## Как проводился обход

Стенд: production-сборка (`pnpm build && next start`), живой Postgres 16, `USE_MOCK_DB=false`,
миграции 0000–0022, dev-учётки трёх ролей, нагрузочные данные `scripts/seed-perf.sql`
(313 пользователей, 5 000 задач, 30 000 сообщений, 1 500 заявок).

Чего обход **не** покрывает: визуальная вёрстка на 375px, загрузка файлов в MinIO/S3

отправка email через реальный SMTP, web push. Эти области нужно проверить руками отдельно.

Приоритеты: **P0** — утечка данных или потеря данных; **P1** — функция не работает или
серьёзный риск; **P2** — неудобство, техдолг, риск при росте.

## P0

### B-01. Новости и база знаний читались без авторизации — исправлено
- **Где:** `GET /api/news`, `GET /api/news/[id]`, `GET /api/knowledge`, `GET /api/knowledge/[id]`.
- **Суть:** `middleware.ts` пропускает весь `/api/*`, а в этих четырёх обработчиках не было
  `requireAuth`. Внутренние новости и статьи базы знаний отдавались любому, кто знает URL.
- **Исправление:** `requireAuth` во всех четырёх обработчиках (`492752f`).
  Регрессию ловят `scripts/audit-route-auth.py` (шаг CI) и `tests/acl`.

## P1

### B-02. Drizzle-репозиторий подмешивал mock-данные при `USE_MOCK_DB=false` — исправлено
- **Где:** `lib/repositories/portal-repository.drizzle.ts` — `getDashboardData`,
  `getSidebarItems`, `getProfileData`, `getCurrentUserProfile`.
- **Суть:** при отсутствии профиля страница `/profile` показывала выдуманного «Петрова Ивана»
  с чужими задачами, отпусками и расчётными листками; пустые телефон и офис заменялись mock-значениями;
  дашборд без `userId` показывал mock-задачи. Sidebar тянул mock-репозиторий (1 744 строки) в client bundle.
- **Исправление:** `97b75c8`. Mock вызывается только из `portal-repository.server.ts` при `USE_MOCK_DB=true`.
  Sidebar — статический конфиг `lib/navigation/sidebar-items.ts`. Тест `tests/repositories/no-mock-fallback.test.ts`.

### B-03. Поиск по чату падал с 500 на реальной БД — исправлено
- **Где:** `GET /api/chat/search`, `lib/repositories/chat-extras.repository.ts`.
- **Суть:** JS-массив id каналов подставлялся в SQL как `($1, $2)::uuid[]` — Postgres отвечал
  `cannot cast type record to uuid[]`. Поиск не работал у любого участника хотя бы одного канала.
- **Исправление:** подзапрос по `chat_channel_members` (`b0a2bb6`).

### B-04. В списке чатов не было последнего сообщения и счётчика непрочитанных — исправлено
- **Где:** `lib/repositories/chat.repository.ts`, `GET /api/chat/channels`.
- **Суть:** результат `db.execute()` проверялся через `Array.isArray`, а node-postgres возвращает
  объект `{ rows }`. Оба списка всегда были пустыми. В TZ v2 пункт «Unread badge» при этом отмечен `[x]`.
- **Исправление:** хелпер `lib/db/rows.ts` + тесты (`b0a2bb6`).

### B-05. `pnpm db:generate` пересоздавал 37 существующих таблиц — исправлено
- **Суть:** миграции 0011–0021 написаны вручную без snapshot-файлов drizzle. Генератор считал diff
  от snapshot 0010 и выдавал миграцию, которая падала бы с `already exists`.
- **Исправление:** baseline-миграция `0022_snapshot_baseline.sql` без DDL (`2bba5b5`).
  Структура сверена: расхождений по таблицам, колонкам, индексам и FK нет (кроме B-11).
  В CI добавлена проверка, что `db:generate` не создаёт новых файлов.

### B-06. Production-сборка зависела от доступа к Google Fonts — исправлено
- **Суть:** `next/font/google` скачивает шрифты при сборке. При недоступном `fonts.gstatic.com`
  `pnpm build` падал (`Can't resolve '@vercel/turbopack-next/internal/font/google/font'`).
  Сборка в закрытом контуре была невозможна.
- **Исправление:** шрифты из `@fontsource/inter` и `@fontsource/exo-2` (`492752f`).
- **Связанное:** `WIDGET_TYPES` вынесен из route handler в `lib/dashboard/widget-types.ts` (`97b75c8`).

### B-07. Внутренний маршрут Python-сервиса пропускал запросы без токена — исправлено
- **Где:** `PATCH /api/v1/protocols/action-items/{id}/status`.
- **Суть:** токен проверялся, только если `INTERNAL_TOKEN` задан. При пустой переменной статус
  поручения менял любой.
- **Исправление:** зависимость `require_internal_token` (fail-closed, сравнение за постоянное время),
  pytest `test_internal_token.py` (`f986bc5`). На портале сравнение тоже переведено на `timingSafeEqual`.

### B-08. Портал отправлял телеметрию во внешнее облако — исправлено
- **Суть:** `@vercel/analytics` подключался в production. Для корпоративного портала с ПДн
  это передача данных о посещениях за пределы контура; на self-hosted сборке скрипт к тому же отдаёт 404.
- **Исправление:** зависимость удалена (`492752f`).

### B-09. Демо-сотрудники создавались с паролем, записанным в репозитории — исправлено
- **Где:** `scripts/seed-demo.ts` (`DEFAULT_PASSWORD = "Temp123456"`).
- **Суть:** если `pnpm db:seed` запускали на стенде, доступном из сети, под любым из 10 демо-сотрудников
  можно войти с известным паролем.
- **Исправление:** пароль берётся из `DEMO_USER_PASSWORD`, иначе генерируется случайный (`1bb72f1`).
- **Действие для ops:** на стендах, где seed уже запускали, сменить пароли или деактивировать демо-учётки.

### B-10. Публичные маршруты Python-сервиса без авторизации — **открыто**
- **Где:** `services/protocols/src/api/v1/protocols.py` — upload, list, detail, export-docx, retry.
- **Суть:** авторизация есть только на портале. Сам сервис на `:8000` отдаёт протоколы совещаний
  любому, кто до него дотянется по сети. Сейчас защита держится на сетевой изоляции.
- **Предложение:** портал добавляет `X-Internal-Token` в `lib/protocols/client.ts`, сервис требует его
  на всех маршрутах `/api/v1/*`. Затрагивает встроенный UI сервиса (`src/web/ui.py`) и Telegram-бота,
  поэтому нужно решение ревьюера. До исправления — убедиться, что порт 8000 закрыт на firewall.

## Что проверено и работает на стенде

Обход 29 страниц под тремя ролями: исключений в браузере и ответов 5xx нет. Сотрудник не открывает
`/admin/*` (403), hr_manager не открывает `/admin/users` и `/admin/tickets` (редирект).
Сотрудник не может согласовать собственный отпуск; не участник канала не читает его сообщения.
Миграции 0020 и 0021 применяются на чистой БД; созданные ими сущности (проекты, шаблоны,
automation rules, опросы, закрепы, папки, комментарии к заявкам, цепочка согласования отпуска)
создаются и читаются через API. Создание задачи с исполнителем без настроенного SMTP не даёт ошибки.
