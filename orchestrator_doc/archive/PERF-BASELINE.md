# PERF-BASELINE — производительность портала СНАРК

Фаза 3 плана доработок. Дата замера: 03.10.2026. **Статус: ожидает согласования целевых чисел ревьюером.**

## 1. Условия замера

| Параметр | Значение |
|---|---|
| Сборка | `pnpm build` (Next.js 16.2.4, Turbopack) + `next start -p 3100`. Замеры `pnpm dev` не использовались |
| Код | ветка `feature/portal-dorabotka`, baseline на коммите `f986bc5` (до оптимизаций) |
| БД | Postgres 16, локально, `USE_MOCK_DB=false`, миграции 0000–0022 |
| Данные | `scripts/seed-perf.sql`: 313 пользователей, 12 отделов, 5 000 задач, 60 каналов / 30 000 сообщений, 1 500 заявок, 400 новостей, 300 документов, 200 статей, 900 отпусков, 6 000 уведомлений |
| Машина | рабочая станция разработчика, Windows 10; портал, БД и клиент на одном хосте |
| Нагрузка | один пользователь, запросы последовательно. Параллельной нагрузки не было |

Инструменты (все в репозитории, замер воспроизводим):

- `python scripts/audit-live.py --runs 8` — TTFB и полное время ответа, медиана по 7 прогонам (первый отбрасывается как прогрев);
- `pnpm test:e2e` (`e2e/page-walk.spec.ts`) + `python scripts/page-walk-summary.py` — LCP в Chromium;
- `python scripts/pg-log-top.py` — топ SQL по логу Postgres (`log_min_duration_statement = 0`).

### Ограничения замера

- Клиент и сервер на одном хосте: сетевой задержки нет. На проде TTFB вырастет на RTT, LCP — на время загрузки бандла.
- Таймер Windows даёт шаг около 15 мс: значения меньше 15–20 мс различать между собой нельзя.
- LCP снят по одному прогону на страницу. Для страниц с разницей в 20–30 мс порядок может меняться.
- Замер однопользовательский. Он показывает стоимость одного запроса, а не поведение под нагрузкой.
- Объём данных — оценка «компания на 300 человек за год». Реальные объёмы СНАРК нужно уточнить.

## 5. Узкие места по убыванию эффекта

| № | Узкое место | Чем подтверждено | Что делать |
|---|---|---|---|
| 1 | Запрос последнего сообщения сортирует все сообщения всех каналов пользователя | 51% времени SQL; `/api/chat/channels` 61–72 мс | `LATERAL` + существующий индекс `chat_messages_channel_created_idx` |
| 2 | Списки без пагинации и с избыточными полями | `/admin/vacations` 984 КБ, `/admin/knowledge` 766 КБ (полный текст 100 статей в списке), `/tasks` 501 КБ (300 контактов для выбора исполнителя) | Пагинация по 50; в списке статей не отдавать `content`; контакты для выбора подгружать по поиску |
| 3 | Поиск по чату — полный скан `ILIKE` | 10% времени SQL, 18 мс на 30 000 сообщений, растёт линейно | Индекс `pg_trgm` по `body` или рабочий `search_vector` (см. BUGS B-11) |
| 4 | Счётчик непрочитанных считает сообщения по всем каналам на каждый запрос списка | 11% времени SQL | Частичный подсчёт только по каналам с `last_read_at < updated_at` или денормализованный счётчик |
| 5 | `/api/tasks/dashboard` делает несколько тяжёлых выборок последовательно | 52–88 мс | Объединить подсчёты в один запрос, выполнять выборки параллельно |
