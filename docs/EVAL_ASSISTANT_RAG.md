# Оценка качества ассистента (этап 5)

Дата: 03.10.2026. **Статус: этап не выполнен. Готов только инструмент прогона.**

## Почему этап не выполнен

Для оценки по заданию нужны вводные, которые исполнителю не переданы:

| Нужно | Для чего | Статус |
|---|---|---|
| 14 HR-документов СНАРК (`BD_main`) | предмет оценки | нет |
| 9 эталонных вопросов | основа датасета | нет |
| Системный промт бота (docx) | промпт сейчас — рабочая заготовка | нет |
| Dev-ключи YandexGPT и GigaChat | сравнение провайдеров | нет |
| Выгрузка логов n8n | сравнение с текущим ботом | нет |

Поэтому **в этом документе нет таблицы метрик по критериям K2–K5 и K8 и нет рекомендации по провайдеру.**
Любые цифры ниже относятся к проверке инструмента на синтетическом документе и о качестве ассистента
на документах СНАРК ничего не говорят.

## Что готово

- `services/protocols/tests/eval/dataset.yaml` — формат датасета и 5 проверочных случаев на
  синтетическом документе (`scripts/make_demo_docx.py`). Категории `cross_doc`, `versions`, `access` пусты.
- `services/protocols/tests/eval/test_eval.py` — прогон `pytest -m eval`, отделён от обычных тестов
  (`addopts = -m 'not eval'`). Считает: попадание ожидаемого документа в top-5, совпадение статуса,
  корректность источника (документ, раздел, версия), долю корректных отказов, утечки по списку запрещённых
  подстрок, латентность p50/p95. Пишет `report-<provider>.json`. Падает при утечке или ответе `answered`
  без верного источника (K4 и K5 не смягчаются).
- `services/protocols/scripts/e5_smoke.py` — проверка боевой модели эмбеддингов без БД.

## Проверка инструмента (не оценка качества)

Стенд разработчика, CPU, `multilingual-e5-large`, LLM — провайдер `fake`, один синтетический документ:

```
cases: 5, hit_at_5: 2/2, status_ok: 5/5, no_answer_refusals: 1/1, source_ok: 2/2, leaks: 0
latency_p50_ms: 246, latency_p95_ms: 278      (без сетевого вызова LLM)
```

Наблюдения, полезные для настоящего прогона:

- Модель загружается 15–85 с (первый раз — со скачиванием 2,2 ГБ), запрос кодируется за ~0,15 с на CPU.
  Латентность ответа будет определяться вызовом LLM, а не поиском.
- На шести синтетических парах «вопрос — фрагмент» косинусная близость: релевантные 0,85–0,86,
  соседние по теме 0,74–0,77, посторонние вопросы 0,68–0,72. Стартовый порог `RAG_MIN_SCORE=0.80`
  выбран по этим шести парам. Это не калибровка: порог нужно подобрать на реальном датасете,
  иначе критерии K2 (полнота) и K3 (100% отказов) не проверены.
- Случаи `pii` и `provocation` в проверочном наборе прошли за счёт порога (LLM не вызывалась).
  Поведение реальной модели на провокациях не проверялось.

## Как выполнить этап, когда появятся вводные

1. Загрузить документы: `pnpm seed:content <каталог> manifest.json` (версии и статусы — из реестра источников),
   опубликовать в `/admin/assistant`.
2. Перенести системный промт в `src/modules/assistant/prompts/answer.jinja2`.
3. Дополнить `dataset.yaml`: 9 эталонных + ≥ 25 своих вопросов по всем категориям, включая `versions`
   (ответ опирается на v1.2), `access` (документ отдела и сотрудник без доступа), `cross_doc`.
4. Прогнать `LLM_PROVIDER=yandex_gpt pytest -m eval tests/eval -s` и то же для `gigachat`.
5. Подобрать `RAG_MIN_SCORE`, повторить, занести сюда таблицу метрик, разбор каждой ошибки,
   сравнение с ответами n8n-бота и рекомендацию по провайдеру.
