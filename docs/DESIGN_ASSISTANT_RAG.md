## 1. Ответы на вопросы этапа 0

### 1.1. Где лежат таблицы протоколов и что будет, если запустить их Alembic на базе портала

- Таблицы `meeting_protocols`, `meeting_action_items`, `meeting_tone_analyses` создаются миграцией
  `20260410_000001_create_protocol_tables.py` в схеме **`public`** той базы, на которую указывает
  `DATABASE_URL` Python-сервиса.
- **Dev:** `services/protocols/.env.example`, `alembic.ini` и `services/protocols/docker-compose.yml` указывают на
  отдельную базу `snark_bot` (`postgresql+asyncpg://user:password@localhost:5432/snark_bot`). Корневой
  `docker-compose.yml` создаёт только `portal_dev`. Оба compose-файла занимают порт 5432, то есть в dev
  задуманы два разных инстанса или две базы на одном.
- **Prod:** в `DEPLOY.md` указано только, что PostgreSQL один, нативный, а `DATABASE_URL` сервиса живёт
  в `.env.local` на сервере. Имя базы в git не зафиксировано. **Нужно уточнить у оператора** (§9, вопрос 1).
- Портал к таблицам протоколов напрямую не обращается: только через HTTP (`lib/protocols/client.ts`).

Что сломается, если Alembic протоколов запустить на базе портала с текущим `env.py`:

1. Таблица `alembic_version` и три таблицы `meeting_*` появятся в `public` рядом с таблицами Drizzle.
   Drizzle о них не знает, конфликта имён сейчас нет, но `public` перестаёт принадлежать одному инструменту.
2. `alembic revision --autogenerate` сравнивает `Base.metadata` со всей схемой `public`. Он увидит ~50 таблиц
   портала как «лишние» и сгенерирует для них `DROP TABLE`. Применение такой ревизии уничтожит данные портала.
3. В обратную сторону: `drizzle-kit push` (или `generate` при дрейфе snapshot) предложит удалить `meeting_*`.

Вывод: миграции ассистента нельзя добавлять в существующее окружение Alembic и нельзя оставлять их в `public`.

### 1.2. Как отделить миграции `rag` от миграций протоколов

Выбран вариант **отдельного окружения Alembic**: каталог `services/protocols/alembic_rag/`, конфиг
`alembic_rag.ini`, запуск `alembic -c alembic_rag.ini upgrade head`.

| Настройка | Значение | Зачем |
|---|---|---|
| URL | `RAG_DATABASE_URL` (база портала), не `DATABASE_URL` сервиса | протоколы и ассистент могут жить в разных базах |
| `version_table_schema="rag"` | `rag.alembic_version` | не пересекается с `public.alembic_version` протоколов, если базы когда-нибудь объединят |
| `include_schemas=True` + `include_object` | в сравнение попадают только объекты схемы `rag` | autogenerate не видит `public` и не может сгенерировать `DROP` для таблиц портала |
| `target_metadata` | отдельный `RagBase.metadata` со `schema="rag"` | модели протоколов в это окружение не попадают |

Отвергнутые варианты:

- *Ветки (branch labels) в одном окружении* — общая таблица версий и общий URL; не работает, когда базы разные.
- *Одна metadata + фильтр по схеме* — ошибка в фильтре снова даёт `DROP` таблиц портала; цена ошибки слишком высока.

### 1.3. Сравнение `documents.department_id` (text) и `users.department_id` (uuid)

Правило портала (`portal-repository.drizzle.ts`, `getDocumentsData`):

```ts
!isPrivileged ? or(eq(documents.access, "public"),
                   eq(documents.departmentId, requesterDepartment ?? "")) : undefined
```

Drizzle передаёт uuid пользователя строковым параметром, сравнение идёт как `text = text`. SQL с тем же результатом:

```sql
u.role IN ('admin', 'hr_manager')
OR d.access = 'public'
OR d.department_id = COALESCE(u.department_id::text, '')
```

Детали, без которых результат разойдётся с порталом:

- Приводить нужно uuid к text, а не наоборот: `d.department_id::uuid` упадёт на пустой строке или мусоре.
- `uuid::text` даёт нижний регистр с дефисами. Портал пишет в `documents.department_id` то, что пришло
  из формы, без нормализации. Если туда попал uuid в верхнем регистре, документ не увидит никто, кроме
  admin/hr — и в портале, и в ассистенте одинаково. Это дефект данных, а не расхождение правил.
- `COALESCE(..., '')` повторяет `?? ""`: сотрудник без отдела видит не-public документы с пустой строкой
  в `department_id`. Поведение странное, но оно портальное; ассистент обязан его повторять (A6).
- Роль и отдел читаются из `public.users` в том же запросе, что и поиск. Из тела запроса не берутся.
- Для статей `knowledge_articles` ограничений по отделу в портале нет: опубликованная статья видна всем.

Правило вынесено в один SQL-фрагмент (`acl.py`), на него написан тест «матрица доступа» и интеграционный
тест на БД. В `BUGS.md` (B-20) предложено привести тип колонки к uuid; до этого ассистент работает с text.

### 1.4. Разделы в docx и номер раздела у чанка

*Не проверено на реальных файлах (§0).* Принято по подсказке задания: заголовки разделов размечены стилем `Heading1`.

- Парсер идёт по телу документа в порядке следования блоков (абзацы и таблицы вперемешку, через
  `document.element.body`), а не по `document.paragraphs`: иначе таблицы теряют своё место в разделе.
- Раздел начинается с абзаца, у которого `style.style_id == "Heading1"`. Сверяется именно `style_id`,
  а не отображаемое имя: в русской локали Word имя стиля — «Заголовок 1», а id остаётся `Heading1`.
- Номер раздела: если текст заголовка начинается с номера (`3.`, `3.1`, `Раздел 3`), берётся он. Если
  нумерация автоматическая (номера нет в тексте, он в `numPr`), номер — порядковый счётчик `Heading1`.
- Текст до первого заголовка — раздел `0` с названием документа (титул, преамбула).
- Таблицы: первая строка считается шапкой, каждая следующая превращается в строку
  «Колонка: значение; Колонка: значение». Объединённые ячейки python-docx возвращает повторно — дубликаты
  подряд убираются.
- У каждого чанка хранятся `section_number` и `section_title`; в текст для эмбеддинга добавляется шапка
  «Документ: … Раздел: N. Название», чтобы запрос «испытательный срок» находил чанк, где этих слов нет в теле.
- Чанк не пересекает границу раздела. Короткий раздел — один чанк.

Если в реальных файлах разделы оформлены иначе (жирный абзац, `Heading2`, ручная нумерация), меняется только
функция определения границы раздела; остальной конвейер от неё не зависит.

### 1.5. Префиксы e5, длина входа, почему параметры n8n не переносятся

- `multilingual-e5` обучена с префиксами. Запрос кодируется как `query: <текст>`, фрагмент документа — как
  `passage: <текст>`. Без префиксов или с перепутанными качество поиска заметно падает. Векторы
  L2-нормализуются, близость — косинус.
- Максимальная длина входа `multilingual-e5-large` — **512 токенов** токенизатора XLM-RoBERTa (SentencePiece),
  включая префикс и служебные токены. Всё, что длиннее, молча обрезается: хвост чанка в вектор не попадает.
- Параметры n8n (500 токенов, перекрытие 100) посчитаны в токенах OpenAI (`cl100k`). Русский текст в
  SentencePiece XLM-R даёт другое число токенов, чаще большее. «500 токенов OpenAI» могут оказаться
  550–700 токенами e5 и не поместиться в окно.
- Модель OpenAI принимала до 8 191 токена, поэтому в n8n точный размер не был критичен. Здесь окно в 16 раз
  меньше, и превышение приводит к тихой потере текста.
- Нарезка n8n шла по всему документу и резала разделы посередине. По требованию задания чанк остаётся внутри раздела.

Стартовые параметры: бюджет **450 токенов e5** на чанк вместе с префиксом `passage: ` и шапкой раздела,
перекрытие **~15%** (до 64 токенов) по границам предложений. Длина считается тем же токенизатором, что
использует модель. После нарезки тест проверяет, что ни один чанк не превышает 512 токенов.

Соответствует §3 задания. Уточнения:

## 3. Схема данных

### 3.1. Схема `rag` (Alembic, окружение `alembic_rag`)

```sql
CREATE SCHEMA IF NOT EXISTS rag;
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE rag.sources (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  source_type     text NOT NULL CHECK (source_type IN ('document', 'article')),
  source_id       uuid NOT NULL,              -- public.documents.id / public.knowledge_articles.id
  title           text NOT NULL,
  version         text,
  content_hash    text,                        -- sha256 файла или текста статьи
  index_state     text NOT NULL DEFAULT 'pending'
                  CHECK (index_state IN ('pending', 'indexing', 'indexed', 'failed')),
  error           text,
  chunk_count     integer NOT NULL DEFAULT 0,
  embedding_model text,
  indexed_at      timestamptz,
  created_at      timestamptz NOT NULL DEFAULT now(),
  updated_at      timestamptz NOT NULL DEFAULT now(),
  UNIQUE (source_type, source_id)
);

CREATE TABLE rag.chunks (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  source         uuid NOT NULL REFERENCES rag.sources(id) ON DELETE CASCADE,
  ordinal        integer NOT NULL,
  section_number text,
  section_title  text,
  text           text NOT NULL,
  token_count    integer NOT NULL,
  embedding      vector(1024) NOT NULL,
  UNIQUE (source, ordinal)
);
CREATE INDEX chunks_embedding_hnsw ON rag.chunks USING hnsw (embedding vector_cosine_ops);

CREATE TABLE rag.queries (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL,
  question     text NOT NULL,
  answer_json  jsonb,
  status       text NOT NULL,                  -- answered | no_info | contradiction | error
  sources      jsonb NOT NULL DEFAULT '[]',
  retrieved    jsonb NOT NULL DEFAULT '[]',    -- [{chunk_id, score}]
  llm_provider text,
  latency_ms   integer,
  error        text,
  feedback     smallint CHECK (feedback IN (-1, 1)),
  created_at   timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX queries_created_idx ON rag.queries (created_at DESC);
CREATE INDEX queries_status_idx ON rag.queries (status, created_at DESC);
```

Внешних ключей из `rag` в `public` нет намеренно: у роли `snark_rag` нет права `REFERENCES` на таблицы
портала, а удаление документа в портале не должно блокироваться ассистентом. Осиротевшие источники
убирает периодическая сверка.

Колонка `chunk_count` добавлена к минимальному составу из задания: по ней админка показывает состояние
индексации без `count(*)` по чанкам.

### 3.2. Изменения в `public` (Drizzle, `pnpm db:generate`)

```ts
ragStatus: text("rag_status").notNull().default("draft")   // draft | actual | archived | excluded
```

Существующие документы получают `draft` и в индекс не попадают до явной публикации (A5).
Для `knowledge_articles` актуальность — `is_published = true`, новых полей нет.

### 3.3. Роль БД

```sql
CREATE ROLE snark_rag LOGIN PASSWORD :'rag_password';
GRANT USAGE ON SCHEMA public TO snark_rag;
GRANT SELECT ON public.documents, public.knowledge_articles, public.users,
                public.employee_profiles, public.departments TO snark_rag;
GRANT USAGE, CREATE ON SCHEMA rag TO snark_rag;
ALTER DEFAULT PRIVILEGES IN SCHEMA rag GRANT ALL ON TABLES TO snark_rag;
```

`SELECT` выдан на `knowledge_articles` дополнительно к списку из A3: без него статьи не проиндексировать (D2).
Схему `rag` и расширение `vector` создаёт владелец базы (`CREATE EXTENSION` требует прав, которых у
`snark_rag` нет); миграции таблиц выполняет `snark_rag`.

## 4. Контракт API

Все маршруты Python требуют `X-Internal-Token` (fail-closed). Порядок работ: сначала Python, потом прокси портала.

### 4.1. `POST /api/v1/assistant/sources/{type}/{id}/reindex`

`type` ∈ `document | article`, `id` — uuid. Тело пустое.

| Код | Тело | Когда |
|---|---|---|
| 202 | `{"source_type","source_id","index_state":"pending","task_id"}` | задача поставлена |
| 401 | `{"detail":"Неверный внутренний токен"}` | нет или неверный токен |
| 404 | `{"detail":"Источник не найден"}` | нет такого документа или статьи |
| 422 | стандартная ошибка валидации | неверный `type` или `id` |

Вызов идемпотентен: задача сама решает, переиндексировать, удалить чанки или ничего не делать.

### 4.2. `GET /api/v1/assistant/sources?type=&ids=`

Состояние индексации для админки: `[{source_type, source_id, index_state, error, chunk_count, version, indexed_at}]`.

### 4.3. `POST /api/v1/assistant/ask`

Запрос: `{"user_id": "<uuid>", "question": "<1..2000 символов>"}`. Других полей нет: роль и отдел
сервис читает из `public.users` сам.

Ответ 200:

```json
{
  "query_id": "uuid",
  "status": "answered | no_info | contradiction",
  "answer": "…",
  "steps": ["…"],
  "responsible": "… | null",
  "deadline": "… | null",
  "sources": [{"source_type": "document", "source_id": "uuid", "title": "…", "version": "1.2", "section": "3. …"}]
}
```

| Код | Когда |
|---|---|
| 401 | нет или неверный токен |
| 404 | пользователь не найден или неактивен |
| 422 | пустой или слишком длинный вопрос |
| 502 | LLM недоступна или вернула невалидный JSON (запрос всё равно записан в `rag.queries` со статусом `error`) |

`no_info` — это ответ 200, а не ошибка.

### 4.4. `POST /api/v1/assistant/queries/{id}/feedback`

`{"user_id": "<uuid>", "value": 1 | -1}` → 204. 404, если запись не принадлежит пользователю.

### 4.5. `GET /api/v1/assistant/queries`

Журнал для админки: фильтры `status`, `feedback`, пагинация; плюс агрегат частых вопросов.
Проверка роли `admin | hr_manager` выполняется на портале (`requireRole`).

### 4.6. Портал

| Маршрут портала | Доступ | Проксирует |
|---|---|---|
| `POST /api/assistant/ask` | `requireAuth`, `user_id` из JWT | 4.3 |
| `POST /api/assistant/feedback` | `requireAuth` | 4.4 |
| `GET /api/admin/assistant/queries` | `requireRole(admin, hr_manager)` | 4.5 |
| `PATCH /api/admin/documents/[id]/rag-status` | `requireRole(admin, hr_manager)` | меняет `rag_status`, затем 4.1 |
| `POST /api/admin/documents/[id]/reindex` | `requireRole(admin, hr_manager)` | 4.1 |

## 5. Последовательности

### 5.1. Индексация (`assistant.ingest_source`)

1. Прочитать источник из `public` (документ: `file_path`, `version`, `rag_status`, `content_type`; статья: текст, `is_published`).
2. Источника нет, либо `rag_status ∉ {actual}` / статья снята с публикации → удалить чанки и запись `rag.sources`, выйти.
3. Формат не docx (D2) → `failed` с понятной ошибкой, выйти.
4. Скачать файл, посчитать sha256. Хеш и версия совпали с `rag.sources` и состояние `indexed` → выйти (идемпотентность).
5. `index_state = indexing`.
6. Парсинг → разделы → чанки → эмбеддинги батчами с префиксом `passage: `.
7. **Одна транзакция:** `DELETE` старых чанков, `INSERT` новых, обновление `rag.sources` (`indexed`, хеш, версия, модель).
8. Ошибка на любом шаге → откат, `failed` + текст ошибки, повтор с экспоненциальной задержкой (до 3 раз).
   Старые чанки при этом остаются: индекс не пустеет из-за сбоя.

Периодическая сверка (Celery beat, раз в 10 минут): актуальные, но не проиндексированные источники;
расхождения версии; источники в `rag`, которых уже нет в `public` или которые больше не актуальны.
K6 (архивный документ пропадает ≤ 1 мин) обеспечивается немедленным вызовом 4.1 при смене статуса и
фильтром `rag_status = 'actual'` в запросе поиска; сверка — страховка.

### 5.2. Ответ (`ask`)

1. Пользователь из `public.users` (активен?), профиль по whitelist: `position_title`, название отдела,
   `start_date`, `contract_end_date`.
2. Эмбеддинг вопроса с префиксом `query: `.
3. Один SQL: векторный поиск по `rag.chunks` + join `rag.sources` + join `public.documents` /
   `knowledge_articles` с условиями актуальности и ACL (§1.3). Берётся top-k = 6.
4. Лучший score ниже порога → `no_info`, LLM не вызывается.
5. Промпт: системный промт СНАРК + профиль + пронумерованные фрагменты (документ, версия, раздел, текст).
6. `generate_structured()` → JSON по схеме.
7. Проверка источников: остаются только ссылки на источники, чьи чанки были в контексте. `answered` без
   единого источника → `no_info`.
8. Запись в `rag.queries` (всегда, включая ошибки и `no_info`), ответ порталу.

## 6. Защита от утечек

| Риск | Мера | Чем проверяется |
|---|---|---|
| Чанк документа чужого отдела | ACL в том же SQL, что и поиск; LLM получает только разрешённые чанки | интеграционный тест на БД: отдел A не получает чанки отдела B |
| Архивный или исключённый документ | условие `rag_status = 'actual'` в запросе поиска, независимо от состояния индекса | интеграционный тест |
| ПДн в промпте | профиль собирается функцией с явным списком полей; SQL выбирает только эти колонки | unit-тест: в промпте нет `inn`, `snils`, `address`, `birth_date`, `phone` |
| Вопрос о другом сотруднике | данные других сотрудников в контекст не попадают вообще; в промпте — прямой запрет | eval-датасет, категория «ПДн» |
| Выдуманная цитата | проверка источников после LLM | unit-тест |
| Подмена прав в запросе | в теле `ask` нет полей роли и отдела | тест контракта |
| ПДн и вопросы в логах | в structlog пишутся id и длительности, не текст вопроса и не профиль | ревью |

Остаточный риск: вопрос сотрудника и фрагменты документов уходят во внешний API LLM (YandexGPT / GigaChat).
Это предусмотрено заданием («кроме вызова российской LLM»), но должно быть отражено в документах по 152-ФЗ.
